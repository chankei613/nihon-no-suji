## マイルストーン

### M1 — 公開APIの配信（**次の判断待ち**）

iOSアプリが実データを取るには `api/*.json` が公開URLで読める必要がある。
GitHub Pages は無料プランの private repo で不可。選択肢：

| 案 | 手間 | 備考 |
|---|---|---|
| **A. 本体repoを public 化** | 最小 | データもコードも全て公開情報・シークレットなし。README/ライセンス整備だけ |
| **B. `api/` だけ公開ミラーrepo + Pages** | 中 | コード・履歴は private 維持。collect.yml から deploy key で push |
| **C. Cloudflare Pages** | 中 | 要 Cloudflare アカウント連携。帯域無制限・高速 |

決めたら:
- [ ] 配信先を用意、`https://<host>/today.json` で疎通確認
- [ ] `ios/DataStore.swift` の `Config.apiBaseURL` を設定
- [ ] `ios/Resources/*.sample.json` を定期更新する仕組み（collect.yml から ios/ へコピー or ビルド時取得）
- [ ] CORS 不要（ネイティブアプリ）だが、Web版を出すなら要設定

### 既知の小さな課題

- カウントダウン系（`days-to-sekki` `days-to-full-moon`）は変化スコアの対象から外すべき（リセット日に「かなり珍しい変化」と誤判定）
- `warned-municipalities` は気象庁のエンドポイント移転リスクが高い（過去に1度移転）。鮮度ガードはあるが監視したい
- 月の出/月の入りの自前計算は ±10分程度の誤差。国立天文台と突き合わせる自動チェックがあるとよい
- `data/history` と `api/` の巨大化（毎時コミット）。数年で肥大化 → 年ごとに履歴を分割 or squash する運用を将来検討

### インフラ / 運用

- [ ] GitHub Actions 無料枠（private 2000分/月）の消費監視。毎時 collect ≒ 720分/月＋test。超えそうなら collect を隔時 or 主要時間帯だけに

- [ ] バックアップ（repo 自体が履歴なので低リスクだが、api の別ホスト化で冗長性）
