# 日本の数字 — 企画書

## 1. 概要

### 仮タイトル
**日本の数字**

### コンセプト
> **昨日から、日本はどう変わった？**

「日本の数字」は、ダム貯水率、気温、湖の水位、電力需要、降水量など、日々変化する日本のさまざまな数値を眺めるためのアプリ。

ニュースアプリでも、統計アプリでも、天気アプリでもない。

**日本という巨大な生き物のステータス画面を見るような感覚で、現実世界の変化を数字として楽しむ。**

役に立つことよりも、

- 昨日より増えた
- 昨日より減った
- 最近ちょっと変
- 今日は大きく動いた

といった「変化」を楽しむことを中心にする。

---

# 2. このアプリが解決したいこと

世の中には膨大な公開データが存在する。

しかし多くの場合、

- 官公庁サイト
- CSV
- PDF
- 統計サイト
- 各自治体
- 電力会社
- 気象データ

などに分散しており、一般ユーザーが日常的に眺める形にはなっていない。

また一般的なデータアプリは、

- 詳細
- 正確
- 高機能
- 分析的

である一方、日常的に「なんとなく開きたくなる」ものではない。

「日本の数字」では、公開データを集約・正規化し、

> **今日の値 + 昨日からの変化**

という極めてシンプルな形にする。

---

# 3. プロダクト思想

## 3.1 数字そのものを楽しむ

例：

```text
💧 ダム貯水率

63.8%

昨日から
+1.7pt ↑
```

情報としてはこれだけでもいい。

「昨日より増えたんだ」

という小さな発見を楽しむ。

---

## 3.2 現在値ではなく「変化」を主役にする

一般的なデータサービスは現在値が主役。

日本の数字では、

```text
現在値
+
前日比
```

をセットで扱う。

例：

```text
67%
```

より、

```text
67%
↑ +4.2pt
```

のほうが、

> 何があった？

という興味につながる。

---

## 3.3 情報を増やしすぎない

このアプリを「総合情報アプリ」にしない。

たとえばダムであれば、

- 所在地
- 建設年
- 歴史
- 観光情報
- 発電設備
- 詳細な水利情報

などを大量に追加しない。

主役はあくまで、

```text
63.8%
↑ 1.7
```

という数字。

---

## 3.4 「役立つ」より「明日も見たい」

採用する数字の判断基準はひとつ。

> **その数字、明日も見たい？**

重要な統計だから採用するのではない。

1日後に数字が変わっていたら、少し気になるか。

これを基準にする。

# 7. 「変化」画面

このアプリの重要機能。

## 今日、大きく動いた数字

```text
🔥 全国最高気温
いつもより +2.3σ

💧 ○○ダム
-4.8pt

🌧 最大降水量
+72mm
```

単位が違う数字をそのまま比較することはできない。

そのため、

> **普段と比べて、どれくらい珍しい変化なのか**

をスコア化する。

---

# 8. 変化スコア

初期案：

```text
変化スコア
=
今日の変化量
÷
過去30日の通常変動幅
```

より実用的には、

- 標準偏差
- MAD（Median Absolute Deviation）
- Z-score
- 過去30日平均との差

などを使う。

これによって、

## 今日の日本で一番「いつもと違う数字」

を出せる。

# 13. comparison_type

数字によって「増減」の表現方法が違う。

### percentage_point

```text
貯水率

50%
↓
55%

+5pt
```

### absolute

```text
気温

30℃
↓
32℃

+2℃
```

### percentage

```text
電力需要

4,000万kW
↓
4,200万kW

+5%
```

そのため、metric側に、

```text
absolute
percentage
percentage_point
```

を持たせる。

# 15. このサービスの本当の資産

アプリそのものだけではない。

日本の公開データは、

- API
- CSV
- HTML
- PDF
- 自治体サイト
- 官公庁サイト

など各所に分散している。

これらを、

```text
取得
↓
正規化
↓
履歴化
↓
差分計算
↓
共通API化
```

する。

つまり長期的には、

> **日本中に散らばった公開データを統一フォーマットにしたデータベース**

そのものが資産になる。

# 16. AIの扱い

MVPではユーザー向けAI機能を入れない。

数字を主役にする。

### 入れない例

```text
AIが今日の日本を解説します
```

### 理由

AIが、

> 昨日の大雨によってダム貯水率が上がりました

など、数字だけから因果関係を推測してしまう危険がある。

「日本の数字」は、

**数字を数字として楽しむ。**

将来的にAIを使う場合も、

- データ分類
- 異常値検出
- データソース探索
- 内部運用

など、裏側を中心に使う。

---

# 23. 開発フェーズ

## Phase 0 — データ調査

まず100候補程度の「数字」を洗い出す。

評価項目：

| 項目 | 内容 |
|---|---|
| 面白さ | 毎日見たいか |
| 更新頻度 | 日次・時間・月次 |
| 取得方法 | API / CSV / HTML |
| 安定性 | 長期間取得できそうか |
| 地域性 | 全国 / 都道府県 / 地域 |
| 保存価値 | 履歴を持つ意味があるか |
| 実装難易度 | 低 / 中 / 高 |

ここからMVPの8個を選定する。

---

## Phase 1 — Collector

各データソースからデータ取得。

```text
fetch
↓
parse
↓
normalize
↓
save
```

Collectorsを独立したモジュールとして作る。

---

## Phase 2 — API

共通フォーマットで、

```text
GET /metrics
GET /metrics/{slug}
GET /metrics/{slug}/history
GET /today
GET /changes
```

などを提供。

---

## Phase 3 — iOS MVP

まず、

```text
今日
数字一覧
詳細
```

を実装。

---

## Phase 4 — 変化ランキング

履歴が蓄積された後、

- 今日大きく動いた数字
- 30日で大きく動いた数字
- 連続上昇
- 連続下降
- 今年最高
- 今年最低
- 平常値からの乖離

などを追加。

---

## Phase 5 — ウィジェット

お気に入り数字をホーム画面へ。
